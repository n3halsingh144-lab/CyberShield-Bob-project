1. Abstract

CyberShield SOC is a browser-based Security Operations Center dashboard developed entirely in Python using the Streamlit framework. The application simulates a real-world SOC environment, providing analysts with a centralized interface to monitor, triage, and manage security alerts and incidents in real time. All data displayed by the application is synthetically generated in-memory using Python's standard library; no live network traffic, external APIs, or databases are used.

The project demonstrates practical knowledge of cybersecurity workflows including alert triage, incident response lifecycle management, chain-of-custody documentation, and evidence logging — all rendered through an interactive, dark-themed web interface that auto-refreshes every five seconds to simulate a live threat feed.

2. Introduction

2.1 Background

A Security Operations Center (SOC) is the nerve center of an organization's cybersecurity posture. SOC analysts monitor security events generated by SIEM (Security Information and Event Management) platforms, triage alerts, escalate genuine threats into incidents, and track those incidents through to resolution. Effective SOC tooling must surface the right information at the right time, support analyst workflows, and maintain an auditable record of every action taken.

2.2 Problem Statement

Students and aspiring security analysts often lack access to realistic SOC tooling for learning purposes. Commercial SIEM products are expensive and complex to configure. This project addresses that gap by providing a fully self-contained, zero-infrastructure SOC dashboard that can be run locally with two pip install commands.

2.3 Objectives

  • Simulate a live alert feed with realistic threat categories and severity levels.
  • Provide KPI summary cards, interactive charts, and a filterable alert table.
  • Implement a complete incident response workflow from alert triage to resolution.
  • Maintain a chain-of-custody audit trail for every incident.
  • Allow report export in plain-text format for submission or archiving.
  • Deliver all functionality in a single Python file without external services.

Why Streamlit?

Streamlit converts Python scripts into interactive web applications without requiring HTML, JavaScript, or a separate frontend framework. Its reactive execution model — where the entire script reruns on every user interaction — pairs naturally with the st.session_state persistence layer used here to maintain the in-memory alert and incident stores between reruns. The built-in st.rerun() call enables timed auto-refresh to simulate live data.

4. System Architecture

4.1 Data Flow

  1. Initialization: _init_state() seeds 40 historical alerts and 5 incident tickets into st.session_state on the very first run.
  2. Live Feed: _maybe_add_alerts() checks elapsed time; if ≥ 5 s, inserts 1–3 new alerts at the front of the list (max 200 kept).
  3. Rendering: The active page function reads from session state, applies sidebar filters, and renders charts, tables, and action widgets.
  4. Mutation: Action buttons (Acknowledge, Escalate, etc.) write back to session state, which persists across reruns.
  5. Auto-refresh: st.rerun() at the end of main() re-executes the script every ~5 seconds.

5. Features & Implementation

5.1 Dark Theme

A GitHub-inspired dark palette is applied by injecting a <style> block via st.markdown(..., unsafe_allow_html=True). Key colours: background #0d1117, surface #161b22, border #30363d, text #c9d1d9. Streamlit's own data-testid selectors are overridden to ensure complete theme coverage including the sidebar and data frames.

5.2 Live Clock

The top bar renders datetime.datetime.now().strftime(...) on every rerun cycle, producing a clock that updates every 5 seconds alongside the alert feed.

5.3 Summary KPI Cards

Four metric cards are rendered using custom HTML/CSS in a 4-column Streamlit layout:

5.4 Alert Generation

Each alert is a Python dictionary with six fields. Severity is weighted to reflect realistic distribution (Low 30%, Medium 40%, High 20%, Critical 10%). Source IPs are drawn from a pool of 70 pre-generated addresses spanning RFC 1918 private ranges and public space.

5.5 Sidebar Filters & Search

The sidebar exposes three st.multiselect widgets (Severity, Type, Status) and a free-text st.text_input for IP or Alert ID search. Filters are applied using Pandas boolean masks on the DataFrame derived from the session-state alert list. All filters are additive (AND logic); the search performs case-insensitive substring matching.

5.7 Alert Actions

A st.selectbox lets the analyst pick any alert visible in the filtered table. Four action buttons mutate that alert's Status field in session state:

  • Acknowledge — sets Status to Acknowledged; confirms receipt of alert.
  • Escalate — sets Status to Escalated; flags for senior analyst review.
  • Mark False Positive — sets Status to False Positive; closes without action.
  • Create Incident — auto-creates an Incident ticket mapped to the alert's severity (P1–P4), assigns a random analyst, and escalates the source alert.

5.8 Incident Management

The Incidents page provides a full ITSM-style ticket workflow. Each incident carries: ID, Title, Priority (P1–P4), Assignee, Status, Created timestamp, Notes, Evidence list, and Chain-of-Custody log.

Status Workflow:

Open → Investigating → Contained → Resolved

Every status transition, note save, and evidence addition appends a timestamped, actor-labelled entry to the incident's immutable Chain-of-Custody log — mirroring real forensic chain-of-custody requirements.

5.9 Report Export

st.download_button streams a formatted plain-text report directly to the browser for download. The report contains all incident metadata, notes, evidence filenames, and the complete chain-of-custody timeline — suitable for submission or archiving.

9. Limitations & Future Scope

Current Limitations

  • All data is synthetic and in-memory — restarting the application resets all state.
  • No user authentication or role-based access control.
  • No persistence layer; a database (SQLite, PostgreSQL) would be needed for production use.
  • Charts use Streamlit's native renderer — advanced visualisations would require Plotly or Altair.
  • Single-user; concurrent multi-analyst sessions are not supported.

Potential Enhancements

  • Real SIEM integration — connect to Elastic SIEM, Splunk, or Microsoft Sentinel via REST API.
  • Database backend — persist alerts and incidents to SQLite or PostgreSQL.
  • Authentication — add streamlit-authenticator for login & role management.
  • Email / Slack notifications — alert on Critical severity events in real time.
  • Threat intelligence enrichment — integrate VirusTotal or AbuseIPDB for IP lookups.
  • PDF report export — replace plain-text with formatted PDF using ReportLab.
  • MITRE ATT&CK mapping — tag each alert type to a MITRE tactic/technique.

10. Conclusion

CyberShield SOC successfully demonstrates the core workflows of a Security Operations Center within a minimal, self-contained Python application. By combining Streamlit's reactive rendering model with in-memory session state, the project delivers a convincing simulation of real-time threat monitoring, analyst triage, incident lifecycle management, and forensic documentation — all without external dependencies beyond two PyPI packages.

The project is a practical illustration of how cybersecurity concepts — alert severity classification, incident response phases, chain-of-custody tracking, and evidence management — can be modelled in software. It serves as both a learning tool for aspiring SOC analysts and a functional prototype that could be extended into a production-grade system with the enhancements outlined above.
